Week 08 — Arduino Core & Libraries

ESP32 Exploration and Library Management

Week 7 approached the ESP32 through ESP-IDF, writing C against Espressif's own drivers. Week 8 came back to the same chip from the other direction: the Arduino core, where most of the low-level work is already wrapped in libraries. The point was not that one approach is better, but knowing which one a given job calls for.

Learning Objectives

  • Add ESP32 board support to the Arduino IDE through the Boards Manager.
  • Find, install, and update third-party libraries using the Library Manager.
  • Understand what a library actually contains and how the IDE finds it.
  • Diagnose version conflicts and missing dependencies.
  • Use a built-in library to drive ESP32 hardware with very little code.

Board Support Comes First

The Arduino IDE does not know about the ESP32 out of the box. Espressif publishes a board package, and the URL for it has to be added under Preferences → Additional Boards Manager URLs before the chip appears in the board list at all.

https://espressif.github.io/arduino-esp32/package_esp32_index.json

With that URL in place, Boards Manager offers "esp32 by Espressif Systems". Installing it pulls down the compiler toolchain, the ESP32 variants, and the upload tool — which is why the first install is a large download and every one after that is quick.

What a Library Actually Is

A library is just a folder the IDE knows where to look for. Inside it there is header and source code, a library.properties file describing the name and version, and usually an examples folder. Those examples matter more than they look: opening one from File → Examples is the fastest way to learn a library, because it is code the author knows works.

MyLibrary/ |-- library.properties # name, version, author, dependencies |-- src/ | |-- MyLibrary.h # the public interface | `-- MyLibrary.cpp # the implementation `-- examples/ `-- Basic/Basic.ino # a sketch that is known to work

Using a Built-in Library

The ESP32 board package ships with WiFi.h, so a network scan needs no external hardware and no extra install. It is a good first test that the board package is working, because a failure here is a setup problem rather than a wiring problem.

#include <WiFi.h> void setup() { Serial.begin(115200); // disconnect from any previous network before scanning WiFi.mode(WIFI_STA); WiFi.disconnect(); delay(100); Serial.println("Scanning..."); } void loop() { int found = WiFi.scanNetworks(); if (found == 0) { Serial.println("No networks found"); } else { for (int i = 0; i < found; i++) { Serial.print(i + 1); Serial.print(": "); Serial.print(WiFi.SSID(i)); Serial.print(" ("); Serial.print(WiFi.RSSI(i)); Serial.println(" dBm)"); delay(10); } } WiFi.scanDelete(); delay(5000); }

Two lines are doing quiet work here. WiFi.scanDelete() frees the results, and without it repeated scans leak memory until the board resets. WiFi.disconnect() before scanning avoids results that are missing networks because the radio was still associated with one.

When Libraries Fight

The cost of using other people's code is that two libraries can disagree. The failures follow a small number of patterns, and recognising them saves a lot of time:

  • Missing dependency — a library depends on another that was never installed, and the error names a header the sketch never mentions.
  • Version drift — example code written for an older release calls a function that has since been renamed, so the library is installed correctly and still will not compile.
  • Duplicate names — two libraries define the same class, and the IDE picks one without being asked. The IDE reports which path it used; that message is worth reading rather than scrolling past.
  • Wrong architecture — a library written for AVR touches registers the ESP32 does not have, and no amount of correct wiring will fix it.

Reflection

Comparing the two weeks directly was the useful part. The ESP-IDF blink from week 7 needed a CMake project, a component file, and an explicit FreeRTOS delay. The Arduino equivalent is a few lines, because the same work is happening underneath where it cannot be seen or changed.

That trade decides which to reach for. Arduino libraries are the right tool for getting a sensor answering quickly. ESP-IDF is the right tool when memory, power, or timing has to be controlled rather than accepted.
