Week 10 — Access Control

RFID Access Control Systems with ESP32

Week 10 took the card reading from week 9 and turned it into a decision. The reader moves to the ESP32, an authorised list is introduced, and the system does something physical when a card is accepted. This is the first project in the course where the code's output is a consequence rather than a message.

Learning Objectives

  • Move the MFRC522 from the Pico to the ESP32 and understand what changes.
  • Compare a scanned UID against a list of authorised cards.
  • Drive an output — LED, buzzer, or relay — based on that decision.
  • Keep the deny path as deliberate as the allow path.
  • Understand where UID-only access control stops being adequate.

Same Module, Different Pins

The MFRC522 does not care which microcontroller is on the other end of the SPI bus, so the module and the protocol are unchanged. What changes is the pin map, because the ESP32 has its own default SPI pins.

MFRC522 ESP32 (VSPI default) --------- -------------------- SDA (SS) --> GPIO 5 SCK --> GPIO 18 MOSI --> GPIO 23 MISO --> GPIO 19 RST --> GPIO 22 3.3V --> 3V3 <-- the ESP32 is a 3.3V part GND --> GND

Both boards being 3.3 V is convenient here: the wiring is a direct swap. The reader is also happier on a steady supply than on a long breadboard run, which is worth remembering when a module reads reliably on one desk and intermittently on another.

The Access Decision

The logic is a comparison, and the honest way to write it is to make refusal the default. The LED and buzzer stand in for a relay or solenoid; swapping the output does not change the structure.

#include <SPI.h> #include <MFRC522.h> #define SS_PIN 5 #define RST_PIN 22 #define GREEN_LED 15 #define RED_LED 2 #define BUZZER 4 MFRC522 reader(SS_PIN, RST_PIN); // UIDs permitted to open the door const char *authorised[] = { "A1B2C3D4", "1A2B3C4D" }; const int authorisedCount = sizeof(authorised) / sizeof(authorised[0]); void setup() { Serial.begin(115200); SPI.begin(); reader.PCD_Init(); pinMode(GREEN_LED, OUTPUT); pinMode(RED_LED, OUTPUT); pinMode(BUZZER, OUTPUT); Serial.println("Access control ready."); } String readUid() { String uid = ""; for (byte i = 0; i < reader.uid.size; i++) { if (reader.uid.uidByte[i] < 0x10) uid += "0"; uid += String(reader.uid.uidByte[i], HEX); } uid.toUpperCase(); return uid; } bool isAuthorised(String uid) { for (int i = 0; i < authorisedCount; i++) { if (uid == authorised[i]) return true; } return false; // deny unless proven otherwise } void grant() { Serial.println("ACCESS GRANTED"); digitalWrite(GREEN_LED, HIGH); delay(2000); // door held open digitalWrite(GREEN_LED, LOW); } void deny() { Serial.println("ACCESS DENIED"); digitalWrite(RED_LED, HIGH); tone(BUZZER, 300, 500); delay(1000); digitalWrite(RED_LED, LOW); } void loop() { if (!reader.PICC_IsNewCardPresent()) return; if (!reader.PICC_ReadCardSerial()) return; String uid = readUid(); Serial.print("Card: "); Serial.println(uid); if (isAuthorised(uid)) { grant(); } else { deny(); } reader.PICC_HaltA(); // stop talking to this card }

PICC_HaltA() at the end is easy to leave out and causes a confusing bug when it is missing: the card stays selected, so a single presentation keeps re-triggering the door for as long as it is held there.

Why the Deny Path Matters

Writing isAuthorised to return false at the end rather than true is a deliberate choice. If the list is empty, if the UID failed to read, or if a future edit adds a branch that falls through, the system refuses. A design that fails open is one where a bug becomes an unlocked door.

The same reasoning applies to logging. Printing every scan, granted or denied, means an unexplained entry can be traced afterwards. A system that only records its successes cannot answer the question people actually ask after an incident.

Honest Limits of This Design

This project works and demonstrates the whole input → decision → output chain, but it should not be mistaken for a secure lock:

  • The UID is broadcast in the clear and can be cloned onto a writable card.
  • The authorised list is compiled into the firmware, so adding or removing a card means reflashing.
  • There is no record of who entered, only what the serial monitor happened to show at the time.
  • Cutting power to the ESP32 stops the reader entirely — what the door does then is a hardware decision, not a software one.

The real fix for the first point is MIFARE sector authentication, where the card proves it holds a key rather than merely announcing a number. The rest are answered by moving the card list off-device and keeping an audit log.

Reflection

This was the week the course stopped being about making hardware respond and started being about what happens when it responds incorrectly. A blinking LED that misreads a button is a nuisance. A door that misreads a card is a different category of mistake, and the code has to be written with that asymmetry in mind.
