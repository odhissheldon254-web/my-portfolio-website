Week 12 — Build, Results & Presentation

Capstone Development and Final Presentation

Week 12 was building AIROS to the design set out in week 11, running the benchmark, and presenting it. The kernel, the Q-Learning scheduler, and the simulation harness came to roughly 750 lines of C11. The benchmark then returned a result that did not match what I expected, and working out why became the most useful part of the project.

Learning Objectives

  • Implement the kernel, scheduler, and benchmark harness designed in week 11.
  • Run all three scheduling modes against an identical workload.
  • Interpret the measurements honestly, including unfavourable ones.
  • Trace an unexpected result back to a specific cause in the code.
  • Present the work, the reasoning, and the limitations.

What Was Built

  • kernel/ — TCB management, simulated Cortex-M context switching, mutexes with priority inheritance, semaphores, and message queues.
  • scheduler/ — the Q-Learning agent: state extraction, binning, epsilon-greedy action selection, and the Bellman update.
  • simulation/ — the three-mode benchmark harness with CSV export.

The Bellman update itself is four lines, which is a fair reflection of where the difficulty in this project actually was — not the learning rule, but everything feeding it.

/* Q(s,a) <- Q(s,a) + alpha * [ r + gamma * max Q(s',a') - Q(s,a) ] */ *q_cur += rl->alpha * (reward + rl->gamma * max_next - *q_cur);

Benchmark Results

Three schedulers, 8 heterogeneous tasks, 5,000 ticks, identical workload:

Scheduler Misses Hits Miss Rate ------------------------------------------------- Fixed Priority 214 4,898 4.19% Round Robin 123 4,939 2.43% AIROS RL-Adaptive 242 4,919 4.69%

The RL scheduler came last. It missed more deadlines than the static baseline it was built to beat, and nearly twice as many as plain Round Robin. Since week 11 committed to "beat Fixed Priority on deadline miss rate" as the success criterion, this run does not meet it.

Why: The Agent Never Finished Exploring

An epsilon-greedy agent takes a random action a fraction epsilon of the time, so that it discovers options its current estimates would never choose. That exploration is not free — in this system a random action means assigning a task a random priority, which sometimes means a missed deadline. It is supposed to pay for itself as epsilon decays and the agent settles into what it has learned.

Mine decays too slowly for the length of the run. Epsilon starts at 0.15 and is multiplied by 0.995 once per epoch — and an epoch is 50 ticks, so a 5,000-tick simulation contains only 100 decay steps:

tick 0: epsilon = 0.150 (15.0% of priority decisions random) tick 501: epsilon = 0.143 (14.3%) tick 2500: epsilon = 0.117 (11.7%) tick 5000: epsilon = 0.091 ( 9.1%) epsilon reaches its 0.01 floor at ~27,050 ticks = 5.4x longer than the benchmark runs

So the agent is still choosing about one priority in eleven at random when the benchmark ends. It never reaches the exploitation phase at all. The measurement is not of a converged adaptive scheduler; it is of an agent still exploring, and the extra 28 misses over Fixed Priority are roughly the price of that exploration.

This also corrects something I had believed earlier. I had described the scheduler as converging around tick 501 — the arithmetic above shows epsilon is still 0.143 there, essentially its starting value. There was no convergence at tick 501, and the reason I thought otherwise is that I read the reward curve flattening as convergence when it was a still-exploring agent's average settling.

What Would Make This a Fair Test

The result is real, but the experiment does not test what it set out to test. Three changes would fix it, in order of how much they would tell me:

  • Run long enough to converge — 30,000 ticks rather than 5,000, so the agent actually reaches its exploitation phase before being judged.
  • Decay faster — 0.95 per epoch reaches the floor in about 2,700 ticks, which fits inside the existing run.
  • Report post-convergence separately — measure the warm-up and the settled phase as two numbers, since a scheduler that pays a one-off learning cost and then outperforms is a genuinely different result from one that simply loses.

Until one of those is run, the honest statement is: on a 5,000-tick benchmark, the RL scheduler does not beat a static priority scheduler, because it does not finish learning within the measurement window.

Presentation

Presenting a result that contradicted my own claim was more useful than presenting a win. The question that came back — whether the RL scheduler was worse or simply unfinished — is exactly the question the epsilon schedule answers, and it is a question I would not have had a good answer to if the benchmark had happened to come out favourably.

Reflection

The engineering lesson has little to do with reinforcement learning. Committing to the success criterion in week 11, before the scheduler existed, is the only reason this result was interpretable. If I had decided what counted as success after seeing the numbers, "Round Robin did best" would have been available as a finding, and the interesting question about exploration would never have been asked.

The second lesson is that a hyperparameter and a benchmark length are not independent settings. Epsilon decay of 0.995 is perfectly reasonable; a 5,000-tick run is perfectly reasonable; together they guarantee the agent is judged before it is ready. Neither number looks wrong on its own, which is precisely why it took a calculation rather than a code review to find.
