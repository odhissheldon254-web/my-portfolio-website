Week 11 — Capstone Design

Capstone Project Component Exploration

Week 11 was spent deciding what the capstone would actually be, before any of it was written. My project is AIROS, a real-time operating system kernel with a reinforcement learning scheduler. The exploration work was scoping: what a kernel minimally needs, what the RL agent would learn from, and why the whole thing would run in simulation rather than on a board.

Learning Objectives

  • Define the scope of a capstone that can be finished and measured.
  • Identify the components an RTOS kernel cannot do without.
  • Decide between hardware deployment and simulation, with a reason.
  • Formulate scheduling as a reinforcement learning problem.
  • Choose an evaluation method before building the thing being evaluated.

Why Simulation Rather Than Hardware

The obvious version of this project runs on the ESP32. I chose simulation instead, and the reason is measurement rather than convenience.

The claim I wanted to test is that an adaptive scheduler beats a static one. Testing that means running three schedulers against the same workload and comparing deadline misses. On real hardware, interrupt timing, flash latency, and Wi-Fi activity all vary between runs, so a difference of a few percent could easily be noise rather than the scheduler. In simulation the tick is deterministic: every scheduler sees an identical task set, and any difference in the results belongs to the scheduler.

The cost of that decision is honest to state — results in simulation are evidence about the algorithm, not proof about a physical device.

Kernel Components

Working out the minimum was the first exercise. A kernel that can schedule anything needs a description of a task, somewhere to keep them, a way to switch between them, and a clock.

  • Task Control Block — id, state, priority, period, deadline, worst-case execution time, plus the runtime statistics the RL agent would later read.
  • Context switch — saving and restoring a simulated ARM Cortex-M stack frame.
  • Tick — a 1 kHz timebase driving deadlines and task releases.
  • IPC primitives — mutexes, semaphores, and message queues, since tasks that never interact do not produce interesting scheduling problems.
#define AIROS_MAX_TASKS 16 #define AIROS_STACK_SIZE 2048 #define AIROS_TICK_RATE_HZ 1000 #define AIROS_SCHED_EPOCH 50 /* ticks between RL scheduler updates */ #define AIROS_PRIORITY_LEVELS 8

One decision here has a consequence that shows up much later. The RL agent updates once per epoch of 50 ticks, not once per tick. That keeps the learning cost away from the scheduling hot path, but it also means a 5,000-tick run gives the agent only 100 opportunities to learn.

Priority Inheritance

Mutexes needed more than a locked flag. If a low-priority task holds a mutex that a high-priority task wants, the high-priority task waits — and any medium-priority task can then preempt the holder, so the most urgent task in the system is blocked by one that is not urgent at all. That is priority inversion, and it is the failure that famously kept resetting the Mars Pathfinder lander.

The fix is priority inheritance: while a task holds a mutex someone more urgent is waiting on, it temporarily runs at that higher priority. The TCB therefore needs both a base_priority and a current priority — which turned out to be exactly the split the RL scheduler needed too.

Scheduling as a Learning Problem

Q-Learning needs three things defined: what the agent observes, what it can do, and how it knows it did well.

  • State — three features per task: deadline urgency, historical miss rate, and burst ratio (recent execution against worst-case). Each is normalised to [0,1] and discretised into 4 bins, because a continuous state space needs function approximation and a binned one only needs a table.
  • Action — assign the task one of the 8 priority levels.
  • Reward — +1 for meeting a deadline, -1 for missing one, a small bonus for keeping utilisation under 80%, and a penalty for starving a task.
#define RL_ALPHA 0.1f /* learning rate */ #define RL_GAMMA 0.9f /* discount factor */ #define RL_EPSILON 0.15f /* exploration rate (epsilon-greedy) */ #define RL_STATE_BINS 4 /* bins per feature */ #define RL_STATE_DIM 3 /* urgency, miss_rate, burst_ratio */

That gives a Q-table of 4×4×4 states by 8 actions per task — 512 entries each, small enough to hold for all 16 tasks and still be plausible on a Cortex-M class device, which was the point of binning in the first place.

Deciding How to Judge It

The last thing settled this week was the evaluation, deliberately before the scheduler existed so the target could not be quietly moved afterwards. Three modes — Fixed Priority, Round Robin, and RL-Adaptive — run against 8 heterogeneous tasks for 5,000 ticks, and the measure is deadline miss rate.

Fixed Priority is the honest baseline: it is what a real RTOS does, so beating Round Robin proves very little and beating Fixed Priority would be the actual result.

Reflection

The most useful part of this week was writing down the success criterion first. It is uncomfortable in a way that turned out to matter — once "beat Fixed Priority on deadline misses" is committed to, the benchmark can return an answer I did not want, and week 12 is where it did exactly that.
