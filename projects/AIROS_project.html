Capstone Project

AIROS: Adaptive Intelligent RTOS

AIROS is a simulated preemptive Real-Time Operating System kernel with three interchangeable schedulers — Fixed Priority, Round Robin, and a Q-Learning reinforcement learning agent that adapts task priorities at runtime from deadline history, urgency and execution-burst statistics.

The finding is negative, and that is the result. On a correctly preemptive simulator with deadlines counted per job, rate-monotonic Fixed Priority beats the learned scheduler decisively — as Liu & Layland's optimality proof says it should for periodic task sets of this shape. An earlier version of this project claimed the opposite; that claim came from a harness in which execution time never occupied the CPU, and it did not survive the harness being fixed.

Written in C11. Explores embedded systems & AI scheduling research on simulated ARM Cortex-M architecture.

Project Architecture

Built entirely from scratch, the AIROS kernel manages up to 16 concurrent tasks using a custom Task Control Block (TCB). The core features include:

  • Simulated context switching using ARM Cortex-M stack frames.
  • Inter-Process Communication (IPC) primitives: Mutexes (with priority inheritance), Semaphores, and Message Queues.
  • Deadline tracking and periodic task releases.
  • Three distinct scheduling policies: Fixed Priority, Round Robin, and the experimental Q-Learning RL agent.

Reinforcement Learning Scheduler

Instead of relying on static priorities set at compile time, the Q-Learning agent observes system state (deadline urgency, miss rate, burst ratio), discretises it into 64 states per task, and assigns one of 8 priority levels using the Bellman update. The policy is ε-greedy with random tie-breaking, warm-started from the static rate-monotonic assignment so it begins as fixed-priority scheduling and learns deviations.

Reward is measured over the whole epoch an action was in force — (hits − misses) normalised to [−1, +1], with a penalty for starving a task beyond twice its own period. The earlier reward read a single instantaneous flag, which scored a task that missed forty deadlines and then met one identically to a task that simply met one.

Benchmark Results

These numbers replace every earlier figure in this project. The original harness ran a task for exactly one tick regardless of its execution time, so nothing ever occupied the CPU and nothing was ever preempted — it measured a queueing policy, not a scheduler. The results below come from a rebuilt preemptive simulator over 20,000 ticks, verified across five random seeds.

Is the Workload Even Schedulable?

The first thing the rebuilt simulator revealed: the documented task set demands 132% of the CPU at worst case and 102% on average, against a Liu-Layland bound of 0.729. It is infeasible — deadline misses are mathematically forced, not a scheduling failure. That was invisible while execution time was free. Both regimes are now measured.

The Honest Conclusion

Fixed Priority wins decisively in both regimes, and the RL scheduler loses. This is the theoretically expected outcome rather than a surprise: Liu & Layland proved rate-monotonic priority assignment is optimal among fixed-priority schedulers for feasible periodic task sets. In the feasible regime there is simply nothing left to win — Fixed Priority already achieves zero misses, so a learned policy can only add noise, and it does.

The overload regime is more revealing. Under overload something must be sacrificed, and the per-task breakdown shows the two schedulers making opposite choices:

Fixed Priority degrades gracefully: it sacrifices the long-period background work and protects the control loop and sensor path almost perfectly. The RL agent does the opposite, spending 436 of its 457 misses on safety-critical tasks to protect a UI refresh and a self-test. In a vehicle or a medical device that is not merely worse — it is dangerous. The cause is ε-greedy exploration: the agent starts warm-started onto a policy that is already near-optimal, so exploration can only move it away, and at 102% load there is no slack to absorb a bad decision.

Rate-monotonic orders tasks purely by period, so it structurally cannot protect a long-period critical task from a short-period trivial one. This task set does not have that property — criticality and rate happen to correlate — which is exactly why it is unbeatable here. A workload where criticality is anti-correlated with period is the problem class where a learned scheduler has real headroom, and is the honest next experiment.

Priority Inheritance, Finally Tested

The kernel shipped mutexes with priority inheritance, semaphores and message queues — and the benchmark never called any of them, so the inheritance branch had never once executed. Adding non-blocking mutex_try_acquire() / mutex_release() entry points made the classic three-task inversion scenario measurable — the same failure mode that kept resetting Mars Pathfinder in 1997:

ConfigurationHIGH task blocked for
Without priority inheritance80 ticks
With priority inheritance20 ticks

The 20 ticks is exactly the remaining critical section — bounded, as the protocol requires. The 80 is that same 20 plus MEDIUM's entire 60 ticks of unrelated work: the unbounded component that grows with however much medium-priority work happens to exist. The kernel's implementation is correct; nothing had ever demonstrated it.
