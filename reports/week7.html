Week 07 — ESP32 & ESP-IDF

Deep Dive into ESP32 and ESP-IDF

Week 6 ended with a setup task: install ESP-IDF and add the Espressif board package before the next class. Week 7 was where that setup got used. The focus moved from the Arduino abstraction to Espressif's own framework, which means writing C against the chip's real drivers and building through a proper toolchain instead of pressing a single upload button.

Learning Objectives

  • Understand what ESP-IDF is and how it differs from the Arduino core for ESP32.
  • Create, configure, and build a project using idf.py and CMake.
  • Use menuconfig to change project settings without editing code.
  • Write firmware around app_main() and FreeRTOS tasks instead of setup/loop.
  • Flash the ESP32 over USB and read output back through the serial monitor.

Why ESP-IDF and Not Arduino

The Arduino core hides a lot. setup() and loop() are convenient, but on an ESP32 they are actually running inside a FreeRTOS task that Arduino created without telling you. ESP-IDF removes that layer: the entry point is app_main(), FreeRTOS is visible, and peripherals are reached through Espressif's own drivers such as driver/gpio.h.

The trade is control against convenience. ESP-IDF exposes memory configuration, partition tables, Wi-Fi stack tuning, and power management — the settings that matter once a device has to run unattended rather than sit on a desk during a lab.

Project Structure and Build System

An ESP-IDF project is not a single sketch file. It is a CMake project with a top-level build file, a main component, and a generated sdkconfig holding every option chosen in menuconfig.

blink/ |-- CMakeLists.txt # top-level project file |-- sdkconfig # generated by menuconfig, not written by hand `-- main/ |-- CMakeLists.txt # registers the source files for this component `-- blink.c # application code

The component file is what tells the build system which sources belong to main:

idf_component_register(SRCS "blink.c" INCLUDE_DIRS "")

Firmware: Blink Written for ESP-IDF

The same blink idea from the early weeks, rewritten the way ESP-IDF expects it. There is no loop function — app_main() is itself a FreeRTOS task, and the delay is vTaskDelay rather than a blocking delay(), so the scheduler can run other tasks while this one waits.

#include <stdio.h> #include "freertos/FreeRTOS.h" #include "freertos/task.h" #include "driver/gpio.h" #include "esp_log.h" #define LED_GPIO GPIO_NUM_2 static const char *TAG = "blink"; void app_main(void) { gpio_reset_pin(LED_GPIO); gpio_set_direction(LED_GPIO, GPIO_MODE_OUTPUT); while (1) { gpio_set_level(LED_GPIO, 1); ESP_LOGI(TAG, "LED on"); vTaskDelay(pdMS_TO_TICKS(1000)); gpio_set_level(LED_GPIO, 0); ESP_LOGI(TAG, "LED off"); vTaskDelay(pdMS_TO_TICKS(1000)); } }

ESP_LOGI is worth noting on its own. It is a levelled logging macro, not a print statement — the verbosity can be raised or lowered in menuconfig, so debug output can be compiled out of a release build without deleting any lines.

Building and Flashing

The toolchain has to be on the path first. ESP-IDF ships an export script for that, and it has to be sourced in each new terminal session.

. $HOME/esp/esp-idf/export.sh # put the toolchain on PATH idf.py set-target esp32 # select the chip idf.py menuconfig # optional: change settings idf.py build # compile idf.py -p /dev/ttyUSB0 flash monitor

flash monitor chains two steps: it writes the binary over USB, then immediately attaches the serial monitor so the ESP_LOGI output appears as the board boots. Ctrl+] exits the monitor.

Note: serial port permissions on Linux

On Linux the board appears as /dev/ttyUSB0 or /dev/ttyACM0, and a normal user cannot open it by default — the flash step fails with a permission error that looks like a broken cable. Adding the user to the dialout group fixes it, but the change only applies after logging out and back in, which is what makes it confusing the first time.

Reflection

The useful lesson was that the Arduino IDE and ESP-IDF are not two ways of writing the same thing. Arduino is a layer sitting on top of ESP-IDF, so everything the Arduino core does is still available underneath — it is just hidden behind defaults somebody else chose.

Seeing FreeRTOS directly also changed how I read the earlier weeks. A blocking delay() in an Arduino sketch is not the CPU stopping; it is one task yielding. That distinction is the whole reason a real device can hold a Wi-Fi connection while still appearing to sit idle in a delay.
